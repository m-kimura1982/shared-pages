# /推敲 — 編集者として、本当に直す必要がある箇所だけを見つける

対象（引数があればそれ、なければ直近で編集した .html）: $ARGUMENTS

## この仕事は何か

**ルール違反を探す仕事ではない。** 表記の揺れを機械的に揃えるのが目的なら check-wording.js だけで足りる。ここでやるのは、**このサイトの編集者として、読者が実際に困る箇所を見つけること**。

直す能力より、**直さない判断のほうが重要**。放っておくと推敲は「何かを直そうとする」方向に流れるので、**「直さなくてよい」を必ず出す**。

`private/推敲対照集.md` は**判断の証拠集であって、チェックリストではない**。「過去にこう判断した」の記録なので、全部を同じ重みで適用しない。似た場面が来たときに引く。

## 手順

### 0. ページ種別と読者を先に決める

同じ文でもページ種別で正解が変わる。**ここを飛ばすと、解説ページの基準をチェックリストに当てるような事故が起きる。**

| 種別 | 読者と用途 | 優先すること |
|---|---|---|
| 加算・解説ページ | 算定の判断をする薬剤師 | 通知の正確さ。原文を載せているなら原文どおり |
| チェックリスト | 印刷して手元で見る | 一瞬で判断できること。正確でも長い文は崩す |
| Q&A | 基本を知ったうえで質問に来た人 | 聞かれたことだけ答える。要件を網羅しない |
| 薬歴マニュアル | 記載する薬剤師 | 記録要素は算定に近くても残す |
| ツールUI | 操作する人 | 敬体。操作の順に書く |
| index / updates | リンクを踏む前の人 | 短い1文。説明を盛らない |
| フォーラム投稿 | 社外の薬剤師 | `/投稿` の文体資料に従う |

### 1. 機械チェックを先に回す

```bash
cd "D:/☆shared-pages"
node assets/check-wording.js <対象ファイル>     # 省略すると公開ページ全部
```

「要修正」は確定ルール違反なので原則そのまま直す。「確認」は文脈しだい。**0件でも推敲は終わらない**（本題はここから）。

### 2. 6層の順に読む。上位層と下位層が衝突したら上位を優先

**1〜3層が本題。4〜6層から入らない。**

| 層 | 見るもの |
|---|---|
| **第1層 意味** | 制度上の意味を変えていないか。通知にないことを書いていないか |
| **第2層 読者** | そのページの読者が一読して意味を取れるか。一文だけ切り出しても通じるか |
| **第3層 構造** | 見出し・本文・ラベル・表・箱の役割が重複していないか |
| **第4層 日本語** | 同僚に口頭で説明するとき、この言い方をするか |
| **第5層 サイト統一** | 用語・文体が既存ページと矛盾しないか（1ページの自然さより統一を優先する場面がある） |
| **第6層 表記** | 数字・かな漢字・プレースホルダ・「〜か月」等 |

CLAUDE.md の7ルールと「内容の混在チェック」4項目は、この層のどこかに必ず入る。

### 3. 重点監査項目

過去に木村さんから指摘を受けた型。**見つけたら疑う**（機械的に直すのではなく、なぜそう書いたかを見てから判断する）。

**まわりくどい名詞化**
- 「〜という判断になる」「〜という関係になる」「〜という形になる」「〜という組み立てになる」→ 動詞で言い切る
- 「〜を意味しない」「〜に準じて」→ 翻訳調・造語

**抽象的な動詞で終わっている**
- 「注意する」「確認する」「把握する」「留意する」で止まっている → **言い換える前に、何が起きるのか・何を防ぐのかが書かれているか見る**。書かれていないなら、そちらを足す（例：「重複になる」で止めず「返戻になる」まで書く）

**指示語で制度上の関係を受けている**
- 「この点数」「この2つ」「そこに」「それ以外」が**算定先・対象・制度上の関係**を指している → 具体的な名称に戻す
- 指示語を全部禁止するわけではない。制度の関係を受けているときだけ

**ラベル・見出しの崩れ**
- ラベルと本文で同じ語を繰り返している
- ラベルが本文の要約にしかなっていない → ラベルごと外す
- 見出しと本文で主語が違う
- テンプレの見出し語をそのまま置いている

**否定から書き出している**
- 「〜ではない」「〜とは限らない」で始まる説明 → **読者が実際にその誤解をするか確認する**。誤解防止が目的でも、まず正しい基準を書き、誤解しやすい点は後ろに分ける

**原文の言い換えに終始している**
- 通知が既に簡潔なら、言い換えても原文に勝てない。価値を出すなら**原文にない軸**（時点・判断基準・実務上の分岐）を足す

**その他**
- 「〜が望ましいと考えられる」のようなぼかしの二重がけ
- 当たり前の因果を理由付きで説明している
- ページ制作者側の言葉（入口・棚・ハブ・核・カード）
- 前の行を読まないと意味が分からない箇条書き

### 4. 「分かりやすくする＝説明を増やす」ではない

**削るほうを先に見る。** 削除候補：

- 当たり前の因果の説明（「返却してからでは写しが取れない」→ 動作だけ残す）
- タイトルの言い直し
- 本文をもう一度言うラベル
- 通知から当然に分かること
- 読者が疑問に思わない否定形の説明
- 別のカードで既に言っていること

**強調は「珍しいほう」に付ける。** 注意喚起を書く前に「これは本当に普段と違うことか」を確認する。

### 5. 提案は3段階に分けて出す。文章の指摘と制度の主張も分ける

いきなり書き換えない。**旧→新の対照表**にして、次の3つに分ける。

- **必ず直す** … 意味が通らない・読者が誤解する・確定ルール違反
- **検討する** … 自然さの問題。採否は本人が決める
- **直さなくてよい** … 引っかかったが、理由があって現状が正しいもの（**必ず書く**）

さらに、**文章として引っかかる指摘**と、**制度として正しいという主張**は別に出す。後者は推敲ではなく制度解釈なので、根拠（別添3の該当箇所・告示）を添えて判断を仰ぐ。

**推敲で判断してよいこと**：語順・冗長さ・指示語の曖昧さ・見出しと本文のずれ・重複・抽象的な動詞の具体化

**推敲だけで判断してはいけないこと**：算定可否／対象範囲／通知の解釈／点数の算定先／「この条件なら必ずこうなる」という制度上の帰結

### 6. 反映と蓄積

本人がOKした項目だけ反映する。そのあと必ず積む（飛ばすと同じ推敲を繰り返す）。

- 機械で検出できる語（旧→新が一対一）→ `assets/wording-rules.json` に1行。**追跡対象なのでもう1台のPCにも届く**
- 判断の理由・見送った理由 → `private/推敲対照集.md` の「9. 個別の直し履歴」に1行
- 足したら `node assets/check-wording.js` を全ページで回し、新ルールが誤検出しないか確認する（するなら `skipSpeech` / `okIfPageHas` / `skipFiles` で絞る）

反映後、必要なら `/公開`（このコマンド自体は push しない）。

## やらないこと

**親切にするために情報を追加しない。** 推敲は文章を直す作業であって、資料を充実させる作業ではない。追加しないもの：

- 制度上の推測
- 読者が疑問に思いそうなことの先回り
- 通知にない数値
- 通知にない「できる／できない」
- 他の点数との比較から導いた結論
- 「おそらく」「一般的には」などの補足

**文章を直すために事実を作らない。**

そのほか：
- 意味・算定要件の正確さを崩す言い換え
- 当社の語り口を無視した全面書き換え（外部提案でも当社の意図を優先する）
- 通知が課している義務の強さを弱めること（やわらげてよいのは口調であって義務ではない）
- 個人情報の追加。draft/ の非公開ルール違反
